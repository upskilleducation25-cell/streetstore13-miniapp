## 1. Аналіз вимог

### 1.1 Що будуємо

Три частини, які працюють з однією базою даних:

| Частина                    | Хто користується    | Де відкривається                         |
| -------------------------- | ------------------- | ---------------------------------------- |
| **Mini App (вітрина)**     | покупці             | всередині Telegram, через кнопку бота    |
| **Адмін-панель**           | власник / менеджери | окремий сайт у браузері (телефон або ПК) |
| **Backend + Telegram-бот** | система             | сервер: API, база, фото, сповіщення      |

### 1.2 Функціональні вимоги (зведено)

**Покупець**

- Головна: логотип, пошук, категорії, «Новинки», «Популярне», «Акції», кошик, нижня навігація.
- Каталог по категоріях (категорії динамічні, з адмінки).
- Пошук: назва, бренд, категорія, артикул. Пізніше AI-пошук природною мовою.
- Картка товару: галерея, назва, бренд, артикул, ціна, стара ціна / знижка, опис, колір, розмір, кількість, залишок, «В наявності / Немає».
- Недоступна комбінація колір+розмір не вибирається.
- Кошик: фото, колір, розмір, кількість, ціна, сума позиції, загальна сума; змінити кількість, видалити.
- Оформлення: ім'я, телефон, місто, служба доставки, відділення/поштомат, коментар. Оплата додається пізніше.
- Підтвердження з номером замовлення.
- Повідомлення від бота про зміну статусу замовлення.

**Адмін**

- Захищений вхід.
- Dashboard: к-сть товарів, к-сть замовлень, нові замовлення, продажі, товари, що закінчуються.
- Товари: створення, редагування, ціна, залишки по кожній парі колір+розмір, фото (додати/видалити/порядок), приховати, видалити; позначки «Новинка», «Популярне», «Акція».
- Категорії: створити, редагувати, видалити, змінити порядок, іконка/зображення.
- Замовлення: список, деталі, зміна статусу (Нове → Підтверджено → Зібрано → Відправлено → Виконано, або Скасовано).
- Налаштування магазину.

### 1.3 Нефункціональні вимоги

- **Швидкість**: перший екран Mini App < 1,5 с на 4G; фото у WebP кількох розмірів через CDN.
- **Mobile-first** і нативне відчуття в Telegram: тема (світла/темна), safe area, системні кнопки Telegram (Back, Main), вібровідгук.
- **Безпека**: перевірка підпису Telegram `initData` на сервері, ціни і залишки рахує тільки сервер, адмінка за паролем і ролями.
- **Цілісність складу**: два покупці не можуть купити останню одиницю одночасно (транзакція з блокуванням рядка).
- **Розширюваність**: оплата, доставка через API Нової Пошти, AI-пошук, промокоди, обране, інші мови додаються без переписування ядра.
- **Мова**: українська за замовчуванням, тексти винесені окремо (готовність до i18n). Валюта: гривня.

### 1.4 Висновки та уточнення з аналізу

1. **Склад ведемо на рівні «варіанту»** (товар + колір + розмір). Саме так можна заборонити вибір відсутнього розміру конкретного кольору і показувати «закінчується».
2. **Ціна на рівні товару**, з можливістю (необов'язково) задати іншу ціну для конкретного варіанту. Знижка вираховується з «старої ціни», окремого поля «відсоток» не потрібно.
3. **Статус «В наявності»** не вводиться руками, а рахується: якщо сума залишків варіантів > 0. Окремо є видимість товару (Чернетка / Активний / Прихований).
4. **Замовлення зберігає «знімок» товару** (назва, колір, розмір, ціна, фото на момент покупки). Якщо потім змінити ціну або видалити товар, старі замовлення не зламаються.
5. **Видалення товару = м'яке видалення** (архів), якщо товар уже є в замовленнях.
6. **Категорії ієрархічні** (поле `parent_id`): зараз 11 категорій верхнього рівня з вашого списку, а підкатегорії можна додати пізніше без змін у базі.
7. **Бренди, кольори, розміри** зберігаються як довідники, а не текстом у товарі. Це дає однакові фільтри та чисті дані для AI-пошуку.
8. **Протиріччя з правилами каталогу STREETSTORE.13**: у збережених правилах магазину сказано «поки без цін», але у цьому ТЗ ціна, стара ціна та знижка потрібні явно. План іде за цим ТЗ (ціни є). Якщо треба запуск без цін, поля просто не показуємо, база від цього не змінюється.

## 2. Архітектура та стек

### 2.1 Загальна схема

```
          ┌──────────────────────────┐
          │        Telegram          │
          │  ┌────────┐  ┌────────┐  │
Покупець ─┼─►│  Бот   │  │Mini App│  │
          │  └───┬────┘  └───┬────┘  │
          └──────┼───────────┼───────┘
       webhook   │           │ HTTPS + initData
                 ▼           ▼
          ┌──────────────────────────┐        ┌────────────────┐
Адмін ───►│      Backend API         │◄──────►│  PostgreSQL    │
(браузер) │  NestJS (Node.js, TS)    │        └────────────────┘
          │  • REST /api/v1          │        ┌────────────────┐
          │  • Telegram bot (grammY) │◄──────►│ Redis (черги)  │
          │  • черга сповіщень       │        └────────────────┘
          └────────────┬─────────────┘        ┌────────────────┐
                       └─────────────────────►│ S3/R2 + CDN    │

                                              └────────────────┘
```

Один backend обслуговує і вітрину, і адмінку, і бота. Фронтенди окремі й статичні.

Якщо пізніше знадобиться публічний сайт магазину з SEO, його можна зробити на Next.js поверх того самого API.

### 2.3 Авторизація

**Покупець (через Telegram, без паролів):**

1. Telegram передає в Mini App рядок `initData` з даними користувача та підписом.
2. Mini App надсилає його на `POST /api/v1/auth/telegram`.
3. Сервер перевіряє HMAC-підпис токеном бота і свіжість `auth_date`.
4. Створюється або оновлюється користувач за `telegram_id`; видається короткий JWT.
5. Номер телефону можна отримати кнопкою «Поділитися контактом» (`requestContact`) на кроці оформлення.

**Адмін:**

- Вхід email + пароль (хеш argon2), сесія в httpOnly cookie, обмеження спроб входу.
- Ролі: `OWNER` (усе, включно з налаштуваннями та адмінами) і `MANAGER` (товари та замовлення). Пізніше можна додати 2FA або вхід через Telegram для адмінів зі списку.

### 2.4 Сповіщення в Telegram

- Адмін змінює статус замовлення → подія `order.status_changed` → задача в черзі → бот надсилає покупцю повідомлення з номером і новим статусом (+ ТТН, коли «Відправлено»).
- Нове замовлення → бот надсилає повідомлення власнику / в службовий чат менеджерів.
- Шаблони текстів редагуються в «Налаштуваннях». Усі відправки пишуться в журнал (успіх / помилка, наприклад, якщо покупець заблокував бота).

### 2.5 AI-пошук (закладаємо зараз, робимо пізніше)

Принцип: **AI не відповідає товарами, він тільки перетворює фразу у фільтр.**

```
«Покажи чорні пуховики до 3000 грн, розмір L»
          │
          ▼
Claude (tool calling) → search_products({
  category: "puhovyky", color: "black", size: "L",
  priceMax: 300000, inStock: true })
          │
          ▼
Backend перевіряє кожне значення по довідниках у БД
(невідомий колір/категорія відкидається)
          │
          ▼
Звичайний SQL-запит до каталогу → реальні товари з БД
```

- Модель отримує тільки список допустимих значень (категорії, кольори, розміри, бренди) і повертає структурований фільтр.
- Ціни, наявність і самі товари завжди беруться з бази, відповідь моделі ніколи не показується як дані про товар.
- Тому вже на 2-му етапі фільтри каталогу проєктуються так, щоб AI-пошук пізніше став просто ще одним способом їх заповнити.

### 4.3 Як працює склад при замовленні

В одній транзакції:

1. Блокуємо рядки потрібних варіантів (`SELECT … FOR UPDATE`).
2. Перевіряємо, що `stock ≥ quantity` і товар активний; ціни беремо з БД, а не з кошика.
3. Зменшуємо `stock`, пишемо `inventory_movements`, створюємо `orders` і `order_items`, очищаємо кошик.
4. Якщо чогось уже немає, замовлення не створюється, а покупець бачить, яка позиція закінчилась.

При скасуванні залишок повертається автоматично.

## 5. API

REST, версія `/api/v1`, JSON, документація Swagger (OpenAPI) генерується автоматично. Пагінація курсорна (`?cursor=…&limit=20`). Помилки в одному форматі: `{ code, message, details }`.

## 7. Як покупець і адмін взаємодіють із системою

### 7.1 Покупець

```
1. Знаходить бота @streetstore13_bot (посилання з Instagram, реклама)
2. /start → вітання + кнопка «Відкрити магазин» (також кнопка меню бота)
3. Mini App відкривається → тихий вхід через initData (без реєстрації)
4. Головна → категорія / підбірка / пошук
5. Картка товару → колір → доступні лише ті розміри, що є в цьому кольорі
   → кількість (не більше залишку) → «Додати в кошик» (вібрація + лічильник)
6. Кошик → змінює кількість / видаляє → «Оформити»
   (якщо поки він був у кошику, товар закінчився — бачить попередження)
7. Оформлення → дані автозаповнюються з минулого разу → «Підтвердити»
8. Сервер перевіряє залишки та ціни, створює замовлення, списує склад
9. Екран «Замовлення № SS13-10024 прийнято» + те саме повідомлення від бота
10. Далі отримує повідомлення в чат бота:
    Підтверджено → Зібрано → Відправлено (з ТТН) → Виконано
    (або Скасовано з причиною)
11. Будь-коли бачить статус у «Мої замовлення»
```

### 7.2 Адмін

```
1. Відкриває адмінку (admin.streetstore13.…) → вхід
2. Dashboard: бачить нові замовлення та товари, що закінчуються
3. Додавання товару:
   «+ Додати товар» → основні дані → ціна → фото → кольори й розміри
   → заповнює матрицю залишків → позначки → статус «Активний» → «Зберегти»
   → товар одразу на вітрині (кеш скидається автоматично)
4. Нове замовлення:
   бот пише у службовий чат «Нове замовлення SS13-10024, 2 позиції, 8 400 грн»
   → менеджер відкриває його в адмінці → телефонує / пише покупцю
   → «Підтверджено» → покупцю йде повідомлення
   → пакує → «Зібрано» → відправляє, вписує ТТН → «Відправлено»
   → після отримання → «Виконано»
   → у разі відмови → «Скасовано» (залишок повертається на склад)
5. Категорії: перетягує, щоб змінити порядок на головній; додає іконки
6. Налаштування: служби доставки, тексти повідомлень, адміни
```

### 7.3 Переходи статусів (сервер не дозволить «перестрибнути» неправильно)

```
NEW ──► CONFIRMED ──► PACKED ──► SHIPPED ──► COMPLETED
 │          │            │          │
 └──────────┴────────────┴──────────┴──► CANCELLED (повернення залишку)
```
